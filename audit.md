Security audit findings (cart/index.html, index.html, checkout/index.html, checkout/checkout.js, cart/cart.js, m8-plate/index.html)

- **Client-side price/data trust** – `checkout/checkout.js` sends `cartItems` from `sessionStorage` directly to `https://api.porchlogic.com/create-checkout-session` and `calculate-shipping-options` without any signing or integrity checks. Cart items are fully editable by a user (prices, quantities, materials, glyph options) because they are stored client-side (`cart/cart.js`). If the backend trusts these values, an attacker can tamper with prices or add arbitrary items before checkout. Mitigation: treat client cart data as untrusted and re-price/re-validate item IDs, quantities, discounts, and shipping server-side before creating a Stripe session.
- **Stored/DOM XSS exposure in cart rendering** – cart UI renders item fields with `innerHTML` using values read from `sessionStorage` (`cart/cart.js`, e.g., the `cart-item-name`, `cart-item-sub`, and summary templates). Because storage is writable by the browser, a malicious script injected via another vector (or a user manipulating storage) can persist script tags in item fields and execute when the cart or checkout pages load. Mitigation: sanitize or escape item fields before injecting into the DOM, or use text nodes instead of `innerHTML`.
- **Stripe key and mode handling** – publishable Stripe keys (live and test) are hardcoded in `checkout/checkout.js`. While publishable keys are not secret, exposing the live key allows anyone to attempt API interactions or phishing overlays mimicking checkout if other controls are weak. Ensure the backend enforces allowed origins, validates server-side prices, and restricts test mode to non-production environments.
